## 二、关键决策说明

### 2.1 签到规则 (D-04)

| 项 | 规则 |
|:---:|:---:|
| 周期 | 自然月, 时区 Asia/Shanghai, 跨月计数清零 |
| 频率 | 每自然日一次, 重复提交返回冲突错误 |
| 单次奖励 | `min(100 + (当月已签次数 - 1) * 10, 200)`, 次数包含本次 |
| 里程碑奖励 | 当月累计第 15 次额外 500, 第 25 次额外 1000 |
| 货币去向 | 余额累积不清零, 变动写入流水 |
| 补签 | 不支持 |
| 并发 | 签到插入与余额更新在同一事务内, 由唯一约束兜底 |

### 2.2 服务端装配 (D-07)

服务端采用 Nitro 主机的组合方式: Nitro 只负责进程与构建产物, 页面渲染关闭, 业务目录不参与 Nitro 路由扫描; 启动插件构造唯一的 Fastify 实例, 中间件把所有请求原样转交。这样既满足需求 R9 (只提供接口), 又让路由, 鉴权与错误处理集中在一套实现里。

### 2.3 原生构建 (D-08)

Android Gradle Plugin 的内置原生构建在开发环境会卡在配置阶段, 因此改为外置脚本: 逐个 ABI 调用 CMake (NDK 工具链) 生成共享库, 复制到打包目录后由 Gradle 直接打包。该决策带来两点约束: 原生库必须先于安装包构建, 且 C++ 运行时使用静态链接以减少依赖。

### 2.4 素材格式 (D-10)

客户端只消费明文容器, 不实现原版的解密加载链; 素材管线另外保留一个编码目标, 把工程文件重新套回原容器并逐字节比对, 用来证明解码没有丢失信息。两条路径互不影响: 明文产物交给客户端, 原容器产物只用于校验。

### 2.5 工程树与产物 (D-11)

解码出的工程树与编码产物体积大且可重建, 因此不纳入版本库; 进版本库的是管线工具, 格式文档, 契约测试与清点报告。带来的约束是: 新环境需要先解码才能编辑素材, 构建客户端前需要先产出运行时二进制。

### 2.6 Java 语言级别 (D-14)

客户端 `sourceCompatibility` 与 `targetCompatibility` 均为 17, 构建期使用 JDK 21。需求基线 R16 表述为 Java, 未锁定具体版本; 若后续需要更高语言级别, 应先升级 Android Gradle Plugin 并重新验证构建链。

## 三、变更方式

- 决策变更新增条目, 保留旧条目并注明取代关系, 不直接改写历史结论
- 决策与代码冲突时, 先核对代码事实, 再决定修正文档还是调整实现
- 涉及需求基线 (R1 至 R18) 的决策变更, 需要用户确认后同步 [requirements.md](requirements.md)
