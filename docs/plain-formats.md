# 明文工程文件规范

> 本文件定义每一类素材的「来源二进制格式 -> 明文工程文件格式 -> 回写方式」三步规约,
> 是 `project/` 树与 `build/` 产物的验收依据, 也是新增格式时对照的模板。
> 容器与字段级结论见 `docs/formats.md`, 流程与命令见 `docs/pipeline.md`。

## 一. 三层模型与不变式

```
来源二进制 (客户端资源树)
        │ decode
        ▼
明文工程文件 (project/<rel> 加 _view/<rel>.json)
        │ encode        │ pack --target plain / --target original
        ▼               ▼
人工编辑            客户端产物 / 校验产物
```

四条不变式, 任一被破坏即视为管线破损:

1. **路径镜像**: `project/<rel>` 与源树里的 `<rel>` 一一对应, 不新增层级, 不改扩展名。
2. **明文一律 UTF-8**: 文本载荷以 UTF-8 无 BOM 落盘; 原始编码, BOM, 换行风格记入索引, 回写时按索引转回。
3. **二进制原样**: 非文本载荷按解密后的原始字节落盘, 结构与字段信息只写进旁挂视图, 不改写载荷。
4. **不丢样本**: 未解格式由兜底编解码器原样保存并记录摘要, 管线不跳过任何文件。

单文件最大 7.3 MiB (`data/csv/csvdef/autogen/itemdef.csv`), 全树 23541 个文件共 879368996 字节。
处理单位是单个文件: 解码, 编码, 摘要全部逐文件进行, 任意时刻不整体载入全树。

## 二. 通用约定

### 2.1 路径与文件角色

| 角色 | 位置 | 是否参与回写 |
|:---:|:---|:---:|
| 明文载荷 | `project/<rel>` | 是 |
| 结构视图 | `project/_view/<rel>.json` | 否, 只读 |
| 索引 | `reports/project-index.jsonl` | 是, 回写参数的唯一权威 |
| 明文产物 | `build/<rel>` | 否, 由工程树生成 |
| 校验产物 | `build-original/<rel>` | 否, 与源逐字节比对 |

视图文件是 JSON, 键排序, 缩进 1, 结尾换行, 内容对同一份载荷稳定可复现。
视图目录以 `_` 开头, 与真实素材路径不会冲突。

### 2.2 文本载荷的落盘与回写

1. 落盘: 按索引里的 `encoding` 解码成字符串, 再以 UTF-8 无 BOM 写入 `project/<rel>`;
   换行符保持原样 (`\r\n` 不转 `\n`), 因为换行风格也记在索引里, 回写需要还原。
2. 编辑: 编辑器必须按 UTF-8 保存; 不要引入 BOM; 不要整体替换换行风格。
3. 回写: 按索引里的 `encoding` 与 `bom` 重新编码; 若编辑引入了该编码无法表示的字符,
   编码会抛异常而不是静默替换, 此时应改索引里的 `encoding` 或退回原字符集。
4. 编码探测顺序: UTF-8 (含 BOM) -> GBK -> GB18030 -> Big5 -> latin-1 兜底;
   latin-1 兜底只保证不丢字节, 内容不可读, 出现在索引里即表示需要人工确认。

### 2.3 二进制载荷的落盘与回写

二进制载荷就是来源字节解密后的结果, 落盘时逐字节复制。
回写走编解码器的 `encode`: 保真级别为 `lossless-passthrough` 的格式直接回写载荷,
保真级别为 `lossless-edit` 的格式按容器参数重新套壳。

### 2.4 明文产物的文本策略

`pack --target plain` 支持两种文本策略, 默认 verbatim:

| 策略 | 文本产物 | 用途 |
|:---:|:---|:---|
| `verbatim` (默认) | 与解密载荷同字节, 保持原编码与原换行 | 客户端消费, 与源同源同字节 |
| `utf8-lf` | 转 UTF-8 无 BOM, 换行统一为 LF | 阅读与 git diff, 不进客户端 |

`--target original` 与策略无关, 始终按索引还原, 与源逐字节一致。

### 2.5 索引字段

| 字段 | 含义 |
|:---:|:---|
| `path` | 相对路径, 与 `project/` 和源树共用 |
| `codec` | 编解码器名, 回写时据此选回同一实现 |
| `fidelity` | `lossless-edit` 或 `lossless-passthrough` |
| `source_size` `source_sha256` | 源文件字节数与摘要, 校验基准 |
| `payload_kind` | `text` 或 `binary` |
| `meta` | 编码, BOM, 换行, 容器参数, 明文长度 |
| `view` | 视图相对路径, 可缺省 |

## 三. 分类规范

### 3.1 数据表 csv

| 项 | 内容 |
|:---:|:---|
| 规模 | 336 个, 29.2 MiB |
| 来源 | 168 个套文本族 `FF D9 FF D7`, 168 个明文 |
| 明文格式 | `project/<rel>.csv`, UTF-8 无 BOM, 保留原换行与列结构 |
| 回写 | 按索引编码转回原编码; 加密族再按 zlib 级别 6 重新压缩并套壳 |
| 现状 | 336/336 逐字节往返通过 |

编码实测 (全量 336 个, 逐个解码判定, 记录在 `reports/census.csv` 的 `encoding` 列):

| 来源 | 编码 | 换行 | 个数 |
|:---:|:---:|:---:|:---:|
| 文本族 | GBK | CRLF | 90 |
| 文本族 | GBK | 混合 | 3 |
| 文本族 | UTF-8 | CRLF | 54 |
| 文本族 | UTF-8 | 混合 | 20 |
| 文本族 | UTF-8 带 BOM | CRLF | 1 |
| 明文 | UTF-8 | CRLF | 145 |
| 明文 | UTF-8 | 混合 | 23 |

结论与操作约束:

1. GBK 只出现在加密族里 (93/168), 明文族的 168 个全部是 UTF-8;
   因此不能按「csv 一定是 UTF-8」处理, 也不能按扩展名分派解码器。
2. 有 1 个文件带 UTF-8 BOM, 明文工程文件里必须去掉 BOM, 回写时按索引补回。
3. 46 个文件是 CRLF 与 LF 混排, 编辑时不要用会统一换行的工具整体改写。
4. 单元格含逗号与引号时按 RFC 4180 处理; 本管线的往返校验只看字节, 不看表格语义,
   改表内容的正确性由使用方自测。

### 3.2 命名区块容器 (omod / emo / ent / otex / oanim)

| 项 | 内容 |
|:---:|:---|
| 规模 | 2098 个容器, 535 个 `.omod` 外面再套一层二进制族 |

| 回写 | 载荷原样回写, 逐字节一致 |
| 现状 | 2098/2098 块序列铺满到文件末尾; 50672 个块中 50643 个由长度闭式闭合 (99.94%), 0 个回退扫描块 |

视图结构:

```json
{
  "container": "named-block",
  "version": 100,
  "block_count": 12,
  "coverage": {"tiles_to_eof": true, "closed_blocks": 12, "scan_blocks": 0},
```

编辑约束: 目前视图是可读的**旁挂产物**, 不是回写输入。改结构 (增删块, 改字段) 需要块写出器,
尚未实现; 现阶段回写只保证「不改载荷就逐字节还原」。字段级 JSON 驱动的回写列为待攻坚项。

### 3.3 纹理 ktx

| 项 | 内容 |
|:---:|:---|
| 规模 | 8736 个, 372.5 MiB, 其中 4368 个套二进制族, 4368 个是裸 KTX 11 |
| 内部格式 | 全量实测只有 `ETC1_RGB8` (0x8D64), 4x4 块 8 字节 |
| 明文格式 | 载荷原样加 `_view/<rel>.json` 头字段视图, 加 `_png/<rel>.png` 的 0 级像素图 |
| 回写 | 像素未改时原样回写; 像素改动后重压块并重算 mip 链 |
| 命令 | `python -m forge.ktx_png stats\|export\|import\|check` |

旁挂路径示例:

```
project/media/ktx/ui/mobile/texture0/main_lobby.ktx      原始 KTX 载荷
project/_view/media/ktx/ui/mobile/texture0/main_lobby.ktx.json   头字段视图
project/_png/media/ktx/ui/mobile/texture0/main_lobby.png        0 级像素 (RGBA)
```

回写规则与代价:

1. 只解 0 级 mip 到 PNG; 低层 mip 与原始文件不再有独立副本。
2. 回写时先比较 PNG 像素与 KTX 解出的像素: 完全一致则保留原字节 (`untouched`),
   有差异才重压块, 并用盒式滤波重算低层 mip (`rebuilt`)。
3. ETC1 是有损压缩, 重压后无法保证与原块逐字节相同, 因此像素级回写属「近似回写」;
   自检命令 `forge.ktx_png check` 报告平均误差与最大误差, 阈值见 `SELF_CHECK_MEAN_LIMIT`。
4. 要求逐字节一致的场景, 走 `--target original` 且不改 PNG: 载荷原样, 天然一致。

校验锚点: 引擎另有 33 字节自定义纹理头, 摘要为 `MD5("miniw20150320\x00" + 正文 + "\x00")`,
可用于验证回写结果。

### 3.4 音频 ogg

| 项 | 内容 |
|:---:|:---|
| 规模 | 2580 个, 104.5 MiB, 1290 个套二进制族, 1290 个明文 |
| 明文格式 | 载荷原样 (标准 Ogg 容器), 加头字段视图 (Vorbis 声道与采样率, 或 Opus) |
| 回写 | 原样回写, 逐字节一致 |

Ogg 是公开格式, 不做结构改写。要换音频就是整文件替换, 之后重跑 `unpack` 让索引跟随源更新。

### 3.5 图标集 ktx 与 xml 布局

| 项 | 内容 |
|:---:|:---|
| 规模 | `ui/` 5352 个文件 188.4 MiB, 其中 `.ktx` 3841, `.lua` 1026, `.xml` 449, 另有 gif 14, omod 6 |
| 纹理页 | 与 3.3 同一条规范, 图集页 `ui/mobile/texture<N>/<page>.ktx`, 像素图在 `_png/` 下 |
| 布局 | `.xml` 走 3.7 (明文或二进制 Android XML) 与 3.1 同类的文本规范; `.lua` 走文本规范 |
| 回写 | xml 与 lua 按索引编码还原; ktx 原样 |

配套关系: 布局 xml 里的控件引用纹理页里的图集条目, 图集条目坐标由纹理页尺寸与布局约定共同决定。
本管线只保证「文件级」的明文与回写, 不解析图集命名空间; 图集语义归客户端渲染层。

### 3.6 体素模型与世界存档

| 来源 | 规模 | 当前状态 | 目标明文格式 |
|:---:|:---:|:---:|:---|
| VMOF `.vmo` | 26 个 | 未接入 | JSON 头加体素数组 |
| MagicaVoxel `.vox` | 6 个 | 未接入 | JSON 体素表 |
| 世界区块 `.r` | 300 个 (292 个 `0C1C0706`, 8 个异形) | 未接入 | JSON 头加数据区 |
| FlatBuffers 容器 `.fcm` | 12 个 | 未接入 | JSON 根表 |

VMOF 目标格式 (版本 100 与 200 共用, 版本 200 多一个尾块):

```json
{
  "magic": "VMOF", "version": 200, "size": [80, 60, 91],
  "voxels": {"encoding": "u16le", "order": "x,y,z 行优先", "data_base64": "..."},
  "tail": {"length": 36360, "data_base64": "..."}
}
```

闭式为 `20 + X*Y*Z*2 + (版本 200 时 4 + 尾块长度) = 文件长度`, 26/26 个样本自洽,
因此该格式一旦接入即可做到逐字节回写, 属 `lossless-edit`。

世界区块 `.r` 目标格式: 头部 35 字节拆成 `{magic, coord:{x,z,levelA,levelB,levelC}, payload_length, const_area}`,
数据区按 `base64` 保存; 坐标区 11 字节的异或密钥 `K = A + 32*B` 由路径决定, 拆解后回写可复现。
数据区编码尚未解出, 因此即使拆了头也做不到语义编辑, 只能原样回写。

| `.essl` | 1614 | UTF-8 1614 | LF 1614 |
| `.hlsl` | 40 | UTF-8 40 | CRLF 40 |

## 六. 校验口径

1. 单条: `forge roundtrip` 对抽样做 解码 -> 明文 -> 回读 -> 编码 -> 与源逐字节比对。
2. 全量: `forge verify --deep` 把工程树里每一条记录重新编码, 与索引里的源摘要比对。
3. 结构: `forge verify` 检查索引与工程树的双向一致, 以及视图文件是否齐全。
4. 清点: `forge census` 产出逐文件编码, 可读性与容器族, 供回归对比。

验收线: 全量深度校验 0 条摘要不符, 0 条编码异常; 抽样往返 200/200 逐字节一致。

## 七. 未支持项与回退策略

| 未支持项 | 影响 | 当前回退 |
|:---:|:---|:---|
| ETC1 像素解码与编码 | 纹理不能改图 | 载荷原样保留, 头视图可用 |
| 命名区块块写出器 | 不能按 JSON 改结构 | 载荷原样保留, 块序列视图可用 |
| VMOF / vox / `.r` / fcm | 体素与存档不可编辑 | 原样保留, 记摘要 |
| axml 回写 | 不能按 XML 重排资源 | 原样保留, 可读 XML 视图可用 |
| WebP 以外的动图容器 | 少数零散格式不可读 | 兜底编解码器原样保留 |
